# GiX-Coder ADR Framework

## Purpose

Architecture Decision Records (ADRs) capture significant architectural decisions, their context, and consequences. They provide a historical record for future maintainers and ensure decisions are deliberate and documented.

## When to Create an ADR

**Required** for:
- New module/service boundaries
- Technology selection (language, framework, database, cloud)
- Security model changes
- Data model changes affecting multiple modules
- API contract changes (breaking)
- Infrastructure architecture changes
- Quality gate changes
- Exception to quality gates
- Phase scope changes

**Optional** for:
- Internal implementation choices
- Refactoring within a module
- Bug fixes
- Documentation updates

### Naming
`NNNN-short-kebab-case-description.md`
- Sequential number (4 digits, zero-padded)
- Descriptive but concise
- Lowercase, hyphens

### Template
```markdown
# ADR-NNNN: <Title>

## Status
Proposed | Accepted | Superseded | Deprecated

## Context
What is the issue? What forces are at play?
Include links to issues, discussions, constraints.

## Decision
What is the decision? Be specific and actionable.

## Consequences

### Positive
- Benefit 1
- Benefit 2

### Negative
- Cost 1
- Cost 2

### Risks
- Risk 1 (mitigation: ...)
- Risk 2 (mitigation: ...)

## Alternatives Considered

### Alternative 1: <Name>
- Pros: ...
- Cons: ...
- Why rejected: ...

### Alternative 2: <Name>
- Pros: ...
- Cons: ...
- Why rejected: ...

## Implementation Plan
- [ ] Step 1
- [ ] Step 2
- [ ] Step 3

## Related
- ADR-XXXX: Related decision
- Issue #XXX
- PR #XXX

## Metadata
- **Author**: Name
- **Date**: YYYY-MM-DD
- **Reviewers**: Name, Name
- **Approved By**: Name (Role)
- **Supersedes**: ADR-XXXX (if applicable)
- **Superseded By**: ADR-XXXX (if applicable)
```

## ADR Lifecycle

### 1. Proposed
- Author creates ADR in `docs/adr/`
- Opens PR with `adr` label
- Minimum 2 reviewers (including architect)
- 5 business days for review

### 2. Accepted
- Approved by architect + domain owner
- Merged to `develop`
- Status updated to `Accepted`
- Implementation begins

### 3. Superseded
- New ADR replaces it
- Old ADR status → `Superseded`
- New ADR references old
- Old ADR references new

### 4. Deprecated
- Decision no longer valid
- No replacement (rare)
- Status → `Deprecated`
- Reason documented

## Review Process

### Reviewers
- **Architect** (required): Architecture alignment
- **Domain Owner** (required): Module expertise
- **Security** (if applicable): Security impact
- **Platform** (if applicable): Operational impact

### Review Criteria
- [ ] Context clearly describes problem
- [ ] Decision is specific and actionable
- [ ] Consequences are honest and complete
- [ ] Alternatives genuinely considered
- [ ] Implementation plan is feasible
- [ ] No conflict with existing ADRs
- [ ] Security implications addressed
- [ ] Operational implications addressed

### Approval
- Minimum 2 approvals (architect + domain owner)
- Security approval for security-related ADRs
- No blocking concerns unresolved

## Quality Gates for ADRs

### Required for Acceptance
- [ ] Follows template exactly
- [ ] Status is `Proposed` initially
- [ ] Number is next sequential
- [ ] No markdown lint errors
- [ ] Links to related issues/PRs
- [ ] Reviewed by required roles
- [ ] No unresolved blocking comments

### CI Validation
- Check template compliance
- Check sequential numbering
- Check required metadata fields
- Generate index automatically

## Anti-Patterns

| Anti-Pattern | Why Bad |
|--------------|---------|
| ADR for trivial decisions | Noise, dilutes important decisions |
| ADR after implementation | Rationalization, not decision-making |
| Vague decisions ("use best practices") | Not actionable, not reviewable |
| Missing consequences | Hidden costs, future surprises |
| No alternatives considered | Confirmation bias |
| Superseding without reference | Lost history, confusion |
| Backdating ADRs | Dishonest history |
